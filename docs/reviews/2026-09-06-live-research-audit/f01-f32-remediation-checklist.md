## Worker stability and latency evidence

The candidate uses canonical records plus one bounded normalized search string per valid record; it does not retain duplicate search-projection objects. CPU profiling identified repeated normalization and repeated query-invariant preparation in the record-scoring hot path. Reusing normalized phrase checks and preparing subject/lexical/exclusion constraints once per request reduced the final fresh-Worker sequence to a 452.5 ms mean across 20/20 identical queries (385.8–553.6 ms), compared with the recorded 354 ms baseline and the superseded 3.252 s candidate run. The same isolate then completed the 47-request audit/homepage replay (287/287 contract checks and 5/5 leaders), exact dataset GET (200, 9,558 bytes, 5.2 ms), Chrome QA, and final health GET without reload, disconnect, 503, or process error. A Worker-mode direct probe remains covered by the 128 MiB V8 old-space check. Current latency receipt: `/mnt/d/tmp/plumbob/ushso-audit-remediation-20260906/worker-latency-receipt.json`.

**Latency acceptance decision:** engineering accepts the measured candidate for review because the warmed mean is now about 1.28× the baseline rather than 9.2×, every measured request remained below 600 ms, and the complete same-isolate workload stayed healthy. This is not a production SLO approval: no formal latency budget or product-owner threshold was supplied, so release owners may still require a stricter target before attestation.

The earlier dataset-detail 503 was not a heap exit: removing the empty `searchDocuments` compatibility property caused `StaticAssetCatalogRepository.getCatalogSummary()` to dereference `undefined.length`; the route catch converted that TypeError to `dataset_unavailable`. Restoring the empty bundle field fixed the exact route. The immutable publication count is now consistently 3,434; invalid isolation remains separately reported as 3,430 searchable plus four partial-result issues.
