## Atomic commits

### C-041-1 — Define the research example packet

Include question, selected products/releases, why each is needed, fields, access steps, tested request, supported join routes, caveats and citations.

**Verify:** A packet is invalid if its source/schema generation differs from an attached request or result.

### C-041-2 — Author representative worked examples

Prepare finance/utilization, staffing/quality, insurance/geography and public-health examples from accepted facts; explicitly state unavailable restricted steps.

**Verify:** Every executed step has a receipt, while a documented but unexecuted step is visibly labeled.

### C-041-3 — Validate examples end to end

Replay eligible bounded requests through the common tester and reconcile their fields and source context. Record expected output shape, not fragile current numeric constants.

**Verify:** A changed source schema invalidates the example and preserves its previous dated version; no live data is fabricated for a demo.

## PR acceptance

- A novice can follow an example without supplying unstated prerequisites.
- An expert can inspect exact source IDs, fields and evidence.

Use the existing affected package tests plus the specific fixtures described below. Add meaningful regression/integration tests for behavior changes; documentation-only commits use link, schema or artifact checks. Full npm test/build/cf:dry-run run at the integration/release gate.

The implementation must demonstrate the behavior above using actual fixtures or retained execution evidence. A source capture is not a payload test; a passing schema is not scientific approval; a successful tool envelope is not a completed research task.
