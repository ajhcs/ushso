# Optional drafting lane

The lane is disabled unless a local operator explicitly supplies `enabled: true`, an execution approval for the exact job, capture hash, rights-file hash, configuration hash, canonical ledger directory, ledger ID, budget scope and worst-case reservation, and a separately vetted provider configuration and credential. No approval, account, provider configuration, activation or live request is supplied here. This package is not connected to the application, publication ledger, or runtime. Its output is a non-authoritative draft requiring human review; unique exact substring validation emits UTF-8 byte offsets and a quote hash; it is not evidence that a claim is supported or true. No approval or publication operation is provided.

`node scripts/source-selection-ai/cli.mjs <init|dry-run|execute|evaluate|status|shutdown|recover-lock|reconcile> input.json` reads an explicit local JSON input. `dry-run` reads and hashes the capture but makes no request. Input must contain only one permitted public capture, never questions or payloads. The input supplies `rights_path` and `rights_sha256` for a separate current policy file. Its bytes are re-read and checked before each dispatch and before returning a draft. Rights records must bind the capture hash and ID, specify `actions.send_to_provider: allowed`, an HTTPS terms URL, reviewer, check time, expiration and current retention. The approval also includes approver, role, issued and expiry times and an attestation. JSON approvals are not cryptographic authorization and file access must be restricted. The operator must verify these declarations and the scope independently; code cannot establish legal rights. Do not put credentials in input files: `provider.key_env` identifies an environment variable. Raw input, responses, credentials and errors are not logged. The returned draft must be handled according to its rights and retention; the package has no response cache. Removing or invalidating the capture or rights blocks future jobs; downstream copies remain the operator's deletion responsibility.

Provider configuration uses the vetted Meta Responses endpoint and `muse-ember-1.0` model, current provider pricing in integer microUSD per million tokens, input and output token limits, bounded timeout and response bytes, zero or one retry, and per-job, monthly and lifetime microUSD limits. The cap covers the configured maximum input and output for every attempt. A provider's actual input token count must fit the cap; the crude byte check is not a tokenizer and does not itself guarantee that. Provider accounting, endpoint semantics, token limits, pricing, organization-level controls and data handling must be verified before any enablement. Configure provider-side limits as well. The adapter requires a usage record for every response, including failures, and reserves the full amount if usage is absent, a request times out, the process crashes, or a result is ambiguous. It cannot establish a hard provider-side charge ceiling if the provider bills beyond the configured accounting assumptions.

Input files and the existing state directory must be regular, non-symlinked paths on the same filesystem as `/workspace`; the state directory must be separate from the capture and rights files. The state directory is private operational data shared by every process using the budget. Each update is fsynced and atomic. A directory lock serializes both reservations and calls; a process crash can leave the lock in place. Treat this as an incident: stop workers, establish whether the provider charged the request and preserve evidence before using the controlled recovery and reconciliation commands below. Never silently release an uncertain reservation. Do not use independent state directories for the same budget, network filesystems with unverified atomicity, or manually edit the ledger during operation. `shutdown` persists a kill switch; a successful shutdown creates a durable stop marker without waiting for the ledger lock. It prevents subsequent starts and retries once observed; a request already starting or in flight may still complete. There is intentionally no CLI reset. A new enablement requires a reviewed operational decision.

`evaluate` accepts one frozen 30-case cohort and separate baseline, assisted, and independently reviewed label files, each pinned to the SHA-256 of `JSON.stringify(cohort)`; cases have unique IDs. Runs supply extraction and review milliseconds per case. Labels supply reviewer, evidence and `critical_approved_error` per case. The result reports total time, critical approved errors and whether zero errors and a proposed 20% reduction were observed. Hashes and declarations do not prove independent review; preserve original timestamps, adjudication, disagreements, and study design outside producer access. No human data are supplied or inferred. This is a proposed decision threshold, not release qualification.

The adapter sets `store: false`, but this does not itself establish zero data retention. Account terms, actual retention and any separately enabled zero-retention arrangement require independent confirmation. References: [Muse Ember](https://dev.meta.ai/docs/muse-ember), [pricing](https://dev.meta.ai/docs/pricing-rate-limits), [Responses protocol](https://dev.meta.ai/docs/protocols/responses), [structured output](https://dev.meta.ai/docs/structured-output), and [terms](https://dev.meta.ai/legal/terms-of-service).

The explicit `init` command fixes the ledger identity, directory, budget scope and per-job, monthly and total budget policy; changing it requires a separately reviewed ledger migration. An unresolved reservation counts against every subsequent month until reconciled. A request that crosses a UTC month boundary is counted in both months, and no retry starts in a later month. The accounting figure charges all observed tokens at the configured uncached rates, so it is a conservative estimate rather than a provider invoice; observed token counts are recorded separately. See [disabled input and evaluation templates](ai-templates/README.md).

Before any job, create an empty private state directory on `/workspace`, supply an enabled config with unique `ledger_id` and `budget_scope_id`, and run `cli.mjs init` with JSON containing `dir` and `config`. The same exact directory, scope and identity must be included in each job approval. Initialization is not paid execution. Deletion of both state and its initialization marker cannot be distinguished from a new directory; retain backups and do not create a second ledger for the same budget scope.

### Interrupted jobs and billing reconciliation

`shutdown` writes the persistent stop marker. `status` reports the current state SHA-256 and each job's fingerprint, or the owner-file hash when a lock is busy. To recover a dead lock, supply `{"dir":"/workspace/.../ledger","expected_owner_sha256":"..."}` to `cli.mjs recover-lock`. Recovery requires the stop marker, the exact owner-file bytes hash, matching host and boot ID, and a PID that no longer exists. Missing, malformed, foreign, live or unverifiable owners fail closed. An immutable recovery receipt is retained. A crash before owner metadata is durable, a reboot that changes boot ID, or a crash leaving the `.recovery` guard requires separate incident investigation; it cannot be automatically recovered by this command. A crash inside recovery can leave the `.recovery` guard; that also stays blocked for operator incident handling. The command does not recursively recover its own guard. A retained recovery receipt is validated and reused on an authorized retry; it is never silently overwritten. Preserve the guard, owner and receipt evidence, and verify that no recovery process is alive before any reviewed operator repair; never automatically delete the guard.

For a `reserved` or `charge_unknown` job, `cli.mjs reconcile` accepts `dir`, `jobId`, `expected_state_sha256`, `expected_fingerprint`, integer `amount_micro_usd`, `billing_evidence_path`, `billing_evidence_sha256`, and `approval`. Billing evidence is a bounded private JSON file with `type: "provider_billing_evidence"`, `job_id`, `ledger_id`, `amount_micro_usd`, `provider_reference` and `observed_at`. The human approval binds `action: "reconcile_charge"`, `evidence_class: "actual_human"`, `job_id`, `ledger_id`, `state_sha256`, `job_fingerprint`, `billing_evidence_sha256`, `amount_micro_usd`, `approver`, `role`, `attestation` and `reviewed_at`. Review must follow the billing observation. The operator independently verifies the provider record and human attestation; these JSON declarations are not cryptographic authentication. The amount cannot exceed the reserved worst case. The exact billing file and immutable reconciliation receipt remain private in the ledger directory, and accounting counts the original and reconciliation months. The stop marker remains in place. No uncertain reservation is automatically released.
